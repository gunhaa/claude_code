# 테스트 & 린트 규칙

---

## 기본 루프 — 반드시 지킨다

```
코드 변경 (작은 단위)
  → 테스트 실행 및 통과 확인
  → 린트 / 포맷 체크
  → 통과하면 커밋
  → 다음 변경으로 반복
```

테스트·린트 실패 상태로는 절대 커밋하지 않는다.

---

## 테스트 실행 명령어

```bash
# 전체 테스트
# <명령어 작성>

# 특정 파일·케이스만
# <명령어 작성>

# 커버리지 포함
# <명령어 작성>

# 테스트 + 린트 한 번에
# <명령어 작성>
```

---

## 린트 / 포맷 명령어

```bash
# 린트 (오류 확인)
# <명령어 작성>

# 자동 수정
# <명령어 작성>

# 포맷터
# <명령어 작성>
```

## TDD 방법론

복잡한 기능은 테스트를 먼저 작성하고 구현한다.

1. **Red** — 실패하는 테스트 작성
2. **Green** — 테스트를 통과시키는 최소한의 코드 작성
3. **Refactor** — 동작을 유지하면서 코드 정리

---

## 테스트 작성 기준

**단위 테스트(Unit Test)**
- 단일 함수·클래스의 동작 검증
- 외부 의존성은 Mock으로 격리
- 파일 위치: `<소스 파일>` 옆 또는 `tests/unit/`

**통합 테스트(Integration Test)**
- 여러 모듈·레이어가 함께 동작하는지 검증
- DB·API 등 실제 의존성 사용 권장 (Mock 과의존 금지)
- 파일 위치: `tests/integration/`

**E2E 테스트**
- 사용자 시나리오 기반 전체 흐름 검증
- 파일 위치: `tests/e2e/` 또는 `e2e/`

---

## Mock 사용 기준

| 상황 | Mock 사용 여부 |
|------|---------------|
| 외부 API (결제, 메일 등) | ✅ 사용 |
| 단위 테스트의 DB 접근 | ✅ 사용 |
| 통합 테스트의 DB 접근 | ❌ 실제 연결 권장 |
| 파일 시스템 (일반적) | ❌ 임시 디렉토리 사용 |

> Mock 과의존 금지: Mock이 통과해도 실제 환경에서 실패하는 사례를 방지한다.

---

## 금지 사항

- `it.skip` / `xit` / `@pytest.mark.skip` 등으로 테스트를 무력화하는 것 (임시라도 커밋 금지)
- 테스트 없이 새 기능 병합 (PR 단계에서 반드시 검토)
- 에러를 숨기는 `try/except pass` 패턴
